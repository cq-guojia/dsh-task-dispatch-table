# 文档规范：放在哪、怎么写

> **这份文档规定本仓库的文档规矩**：写新文档时放哪、叫什么、写什么、什么时候归档。
> 写文档前、归档案前先看这份。规则真源在 [`../RULES.md`](../RULES.md)（用户独占维护）。
> **最后更新**：2026-10-01。

---

## 一、目录：只允许这三个层

```
docs/
  README.md              本文件（文档规范）
  PROGRESS.md            现场层·进行中
  PROGRESS-HISTORY.md    现场层·已结案
  worklog/               叙事层：一个工作包一个文件
  design/                定型层（专题文档 + features/ 功能文档 + external/ 外部事实）
  images/                README 截图（对外文档的配图，kebab-case 命名）
  examples/              样例与模板（与代码零耦合）
```

| 层 | 落位 | 装什么 | 规矩 |
|---|---|---|---|
| **现场·进行中** | `docs/PROGRESS.md` | 「当前状态 / 未决项 / 下一步」三块 | **详细到「下一步具体要做哪一步」**；只装在办的事，结案即移出 |
| **现场·已结案** | `docs/PROGRESS-HISTORY.md` | 一行一条：**时间 / 完成了什么 / 过程文档在哪** | 只记结果与去向，不写过程、不写注意事项 |
| **叙事** | `docs/worklog/<工作包名>.md` | 一个工作包的过程：需求原话、过程、定位、踩坑、证据 | 一个工作包一个文件；**封卷后不得再改**，过程只看这里 |
| **定型** | `docs/design/*.md`（可分子目录） | 以后一直要遵守的东西 | 改它 = 改规矩 |
| **样例** | `docs/examples/*` | 样例、模板 | 与代码零耦合 |

**三者的关系**：`PROGRESS.md` 说「现在做哪一步」→ `worklog/` 说「当时怎么做的」→ 结案后 `PROGRESS.md` 里那一条搬进 `PROGRESS-HISTORY.md` 变成一行，详细过程留在 worklog 不动。

⚠️ `docs/` 之外不建文档；源码 / 脚本 / 构建产物按各自技术栈摆，不在文档体系内登记。

## 二、文档分类与落位（写之前先定类）

| # | 类 | **必须放这** | 文件名 | 写什么 |
|---|---|---|---|---|
| 1 | **进度** | `PROGRESS.md`（进行中）+ `PROGRESS-HISTORY.md`（已结案）+ `worklog/` | `worklog/<工作包名>.md` | PROGRESS：现在做哪一步、欠什么；HISTORY：结案一行（时间 / 完成了什么 / 过程文档）；worklog：做的过程与踩坑 |
| 2 | **数据库** | `design/data-model.md` | 固定 | 表结构、DDL、字段语义、取舍 |
| 3 | **样式** | `design/ui-foundation.md`（方案）+ `design/ui-style-guide.md`（手册） | 固定 | 方案 = **抽象清单**：哪些样式因多处共用要抽出来、抽到哪、为什么；手册 = **使用规范**：写界面时哪些必须复用、哪些可以自己写、写在哪 |
| 4 | **方法** | `design/code-conventions.md`；架构（分层 / 目录 / 职责）附 `design/architecture.md` | 固定 | 通用能力分几类、各抽象在哪、哪些必须复用、不满足需求时怎么提 |
| 5 | **功能** | `design/features.md`（总索引）+ `design/features/<功能>.md` | `features/<功能>.md` | 有哪些功能、每个干什么、对应哪个页面 / 文件、该功能的业务规则（如状态机 `state-machine.md` 属调度功能） |
| 6 | **外部事实** | `design/external/dsh-capabilities.md` / `design/external/session-view-ui-map.md` | 按主题 | 宿主（DSH）能提供什么，源码级核实结果；官方 UI 元素对照 |
| 7 | **对外** | 根 `README.md` | 固定 | 是什么、怎么装、怎么用 |

**归类规则**：先问「这条信息会过期吗」定层，再按上表定类与落位。一层一类只有一个真源文件。

## 三、命名

| 规则 | 说明 |
|---|---|
| 纯 ASCII 小写 kebab-case | `ui-style-guide.md`、`feature-main-panel.md` |
| **表角色，不表时间** | 不带日期、不带版本号；版本历史交给 git |
| 方案 vs 手册分开 | `*-foundation.md` = 为什么这么设计；`*-guide.md` = 怎么做；两者内容不重复 |
| 功能类统一进 `features/` | 避免与 `worklog/` 同名混淆 |
| 工作包文件名 = 工作包名 | `worklog/ui-foundation.md` |

## 四、每类文档怎么写

### 4.1 通用头（定型层文档必带）

```markdown
# <标题>

> **状态**：📝 待拍板 / 🔵 落码 / ✅ 完成封卷
> **来源**：需求出处（用户原话 / 决策编号）
> **配套**：相关文档链接
```

### 4.2 各类的内容要求

| 类 | 必须写 | **不得写** |
|---|---|---|
| 进度（PROGRESS） | 当前状态 / 未决项 / 下一步三块；「下一步」要写到**具体做哪一步** | 已结案的内容（须移入 `PROGRESS-HISTORY.md`）、长篇历史、方案论证 |
| 历史（HISTORY） | 一行一条：时间 / 完成了什么 / 过程文档链接 | 过程、踩坑、注意事项（这些归 worklog） |
| 叙事（worklog） | 需求原话、过程、定位、踩坑、证据（出处 `文件:行号`） | 结论性规矩（应升格到定型层） |
| 定型（design/*） | 是什么、怎么做、边界（不做什么） | 进度、过程日志 |
| 外部事实 | 头部必带「**类型 / 适用版本 / 来源**」——适用版本写清是哪个包哪个版本（宿主升级后据此复核）；正文每条结论带出处（包版本 / `文件:行号`） | 猜测、未核实内容；写成"我们的设计" |
| 功能 | 功能名 / 干什么 / 对应页面与文件 / 状态 | 实现细节（归 worklog） |
| 对外（根 README） | 是什么 / 怎么装 / 怎么用 | 内部设计 |

## 五、生命周期（写完怎么办）

1. **开工**：建 `worklog/<工作包名>.md`，过程实时写进去。
2. **推进中**：就地更新 `PROGRESS.md` 的「当前状态 / 未决项 / 下一步」，过程日志不进现场层。
3. **收尾**：worklog 头部标「✅ 完成封卷」，此后不再修改；`PROGRESS.md` 里该条**移入** `PROGRESS-HISTORY.md`，只留一行（时间 / 完成了什么 / 过程文档链接）。
4. **有定型内容**：升格到 `design/` 对应类文件，原处只留链接。
5. **有遗留问题**：写进 `PROGRESS.md` 未决项，**不回头改已封卷的文件**。

## 六、硬规则

1. **真源唯一**：每类信息只有一个真源；README / issue / 聊天记录都不是真源。
2. **不许两份副本**：同一结论存两处，必有一份过期。规范只在本文件，其它文档只链它。
3. **现场层恒定小**：`PROGRESS.md` 只装在办的事，结案即移入 `PROGRESS-HISTORY.md`；变大即失控。
4. **封卷不改**：叙事层文件封卷后只读；新发现写新文件。
5. **先归位再写**：新建文档前先按 §二 定层、定类、定落位。
6. **结论可追溯**：定型与外部事实类，每条结论必须带出处（`文件:行号` 或包版本）。
