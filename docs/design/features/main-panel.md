## 一、已拍板口径

| # | 项 | 口径 |
|---|---|---|
| 1 | 整体形态 | 内容列**限宽居中**，非全屏铺满：`min-width: 760px` / `max-width: 1120px`（长屏不再被拉成一条）。宿主 `main` 槽仍是整页，右侧文件预览 dock 挤窄整页时内容列随之收窄 |
| 2 | 顶部 | 标题在左；右上角「＋ 新建」按钮；筛选 tabs = **全部 / 已开启 / 已关闭** + **工作区筛选**；带**搜索框**（按标题、编号过滤） |
| 3 | 状态灯（最左色点） | 绿 = 已启用、计划正常运行（含从未执行过的新任务）；红 = 最近一次执行失败；灰 = 已关闭。**运行中 = 转圈 spinner，优先级最高，盖过色点** |
| 4 | 关闭态冲突规则 | 已关闭一律灰（即便上次失败）——灰表达「不跑」，红留给「在跑但出过错」 |
| 5 | 排序 | ① 运行中（转圈）最顶 → ② 已启用：按**下次预计执行时间升序**（马上要跑的最上）→ ③ once 已完结（无下次执行）：启用组末尾，按最后执行倒序 → ④ 已关闭：沉底，组内按上次执行倒序 |
| 6 | 右侧操作 | ① 启用 / 停用 **Switch 拨片**（复用现成 `POST /tasks/enabled`，独立实时写回，不走保存链路）② 编辑按钮（拉起现有编辑抽屉）③ 展开箭头（就地拉伸，不进编辑页） |
| 7 | 承载力 | 任务列表为轻卡片，**大几百条直接全渲染**；不做分页、不做虚拟化。真到撑不住再加懒加载 |
| 8 | 任务简介 | **本轮不实现**（不接 LLM）。按仓库「正常功能禁止模拟数据」规则：未接前卡片**不显示简介行**，也不造假文案占位 |
| 9 | 本轮范围 | 只做任务列表视图；执行记录 / 审计 / 调试债清理不在本包 |
| 10 | 实时性 | 服务端**内存摘要 + 事件驱动增量更新**；客户端**轮询只读内存快照 + revision 比对**（见 §四）。**轮询间隔 10s** |
| 11 | 数据存放 | **不引入派生表**（用户拍板）：运行状态只维护在**进程内存**中，启动时一次初始化，运行中由 Loop A/Loop B 增量维护，丢了可从 `task_instances` 重建 |
| 12 | 动画 | 状态变化导致卡片「下去 / 上来」时**要有动画**（自研 FLIP，不引包）。见 §四.5 |

## 二、卡片布局规格

### 2.1 收起态

```
┌────────────────────────────────────────────────────────────┐
│ ●  每日镜像升级巡检                    [ ●━] [编辑] [⌄]    │
│    每 10 分钟 · 上次 11:30 成功 · 下次 11:54（10 分钟后）   │
│    创建于 9 月 28 日                                        │
└────────────────────────────────────────────────────────────┘
```

| 区 | 内容 | 说明 |
|---|---|---|
| 状态点 | 色点 / spinner | 见口径 3、4 |
| 标题 | 任务名称（有编号时「[编号] 名称」） | 与前置任务下拉同一格式（既有惯例） |
| 信息行 1 | **执行方式人话**（复用现有 `describeSchedule`）+ **上次执行**（时刻 + 成败）+ **下次预计执行**（绝对时刻 + 相对时间） | 相对时间「10 分钟后」由客户端本地每秒重算，不依赖请求 |
| 信息行 2 | **创建于 X** | 需新增 `createdAt` 字段（见 §五 ①） |
| 右侧 | Switch / 编辑 / 展开 | Switch 用官方 `Switch`，编辑与展开用图标按钮（26px、hover 底对齐官方惯例） |

> 「执行方式」必须有：这是用户点名要的第一块内容。标题 + 创建时间 + 执行方式 = 卡片的最小信息集。

### 2.2 展开态（就地拉伸，高度变大，上方原样保留）

下方新增区块，四项：

| 区块 | 内容 |
|---|---|
| 执行设置 | 排期人话 / 工作区 / 模型 / 重试次数 / 允许延迟（真实值，缺则显示「未设置」） |
| 附加文件 | 文件名列表（`link` 标工作区路径，`upload` 标文件名） |
| 前置任务 | 「[编号] 名称（工作区）」列表，停用项标「（已停用）」 |
| 提示词 | **只显示前一段**（约 200 字，超长截断），想看全文点「编辑」进编辑器 |

- 展开才渲染这些内容（不展开不生成 DOM/不读细节）。
- 展开态不提供编辑，只做查看。

## 三、状态与排序（判定口径）

| 状态 | 判定依据 |
|---|---|
| 运行中 | 内存摘要 `running = true`（存在 `dispatched` / `running` 实例） |
| 红 | `lastStatus = 'failed'`（含派发失败） |
| 灰 | `enabled = false` |
| 绿 | 其余（含从未执行过的新任务） |

- 「上次执行」= `lastScheduledAt`（展示时刻）+ `lastStatus`（成功/失败文案）。
- 「下次预计执行」= `nextSlotAt`；一次性任务已到终态 ⇒ 无下次 ⇒ 展示「已结束」并归入排序第 ③ 组。
- `unknown`（重启孤儿）不长期显示为运行中转圈：沿用现有 30 秒宽限收口后，内存摘要跟着置 `running=false`。

## 四、数据方案与效率（本文件核心）

### 4.1 原则

**轮询不查库。** 三类数据分层处理，避免「每 30 秒对 N 个任务各查一遍」。

| 数据 | 变化频率 | 策略 |
|---|---|---|
| 任务定义（标题/排期/设置/附件） | 仅用户保存时 | 客户端缓存 + **revision 比对**，变了才回全量 |
| 运行中 | 高频、易失 | **服务端内存 Map** |
| 上次执行时刻 / 成败 | 一天几次 | **内存摘要 + 事件驱动增量更新** |

### 4.2 服务端内存摘要

```ts
type TaskRuntime = {
  taskId: string
  running: boolean
  runningSince?: string
  lastStatus?: 'succeeded' | 'failed' | 'skipped' | 'unknown'
  lastScheduledAt?: string
  lastFinishedAt?: string
  nextSlotAt?: string | null
}
```

维护点（全部是**顺手更新**，不新增查询）：

| 时机 | 动作 |
|---|---|
| 插件启动 / 首次请求 | **一次聚合 SQL 建索引**（`GROUP BY task_id` + `MAX(scheduled_at)`，走已有 `idx_instances_slot(task_id, scheduled_at)`）+ 逐条算 `nextSlotAt` |
| Loop A 落库 `dispatched` | 该任务 `running = true` |
| Loop B 实例进终态 | 该任务 `running = false` + 写 `lastStatus/lastFinishedAt`（Loop B 本来就在写这一行） |
| 任务保存 / 删除 / 启停 | 只重算该条 `nextSlotAt`，`revision++` |

> **启动时不是清空内存，而是用库里 `status IN ('dispatched','running')` 的行重建**：重启后的在飞行是真实孤儿（U1 已知问题），一次扫描成本几十行；真卡死的由现有 30 秒宽限收口，内存随之清除。

### 4.3 接口契约

`GET /api/task-dispatch-table/tasks/overview?rev=<n>`

- `rev` 未变 ⇒ `{ ok: true, unchanged: true }`（几十字节，零负载）。
- 变了 ⇒ `{ ok: true, rev, tasks: [{ id, title, code, enabled, workspace, scheduleText, createdAt, running, runningSince, lastStatus, lastScheduledAt, lastFinishedAt, nextSlotAt }] }`。
- 展开态所需的**细节**（附加文件 / 前置任务 / 提示词首段）**不进 overview**；展开时按需取（复用 `GET /tasks/history` 或新增按 id 的详情端点），做到「不展开不读」。

### 4.3.1 同步总纲（2026-09-30 抽象统一，本文件为唯一定义）

**所有写路径只调一个入口**；新增写路径时**只在这里加一处**，不在各 handler 里散着改内存：

| 层 | 唯一入口 | 做什么 |
|---|---|---|
| 服务端 | `resyncTaskMap()`（`src/index.ts`）= `safeTick()` + `runtimeIndex.markDefinitionsChanged(...)` | 重解析任务表 → 刷新 `panelTaskMap`；重算展示指纹与下一刻度并按需 `rev++` |
| 客户端 | `overview.refresh()`（`useTaskOverview`） | 立刻重拉一次（在途则记为待办，那轮结束补跑，绝不丢） |

- **写路径**（4 条：整批保存 / 单条保存 / 删除 / 启停）统一调用 `onDefinitionsChanged()` → 上面那个入口。
- **`rev` 的两个指纹分工**：`overviewKeyOf`（覆盖**全部展示字段**）管 rev；`scheduleKeyOf`（排期 + 启停）只管是否重算 `nextSlotAt`。
  > ⚠️ 历史 bug：rev 过去只由排期驱动 ⇒ 改标题 / 提示词 / 附件永远回 `unchanged` ⇒ 界面不刷新。现在由 `overviewKeyOf` 兜住。
- **停用任务没有下次刻度**：`enabled === false` ⇒ `nextSlotAt = null`（所有出口统一，前端显示 `--:--`）。
- **运行中不覆盖上次执行**：`markDispatched` 只置 running；只有 `markTerminal`（出了成功/失败）才覆盖 last*。

### 4.4 客户端刷新

- 轮询：**10s**。
- **无手动刷新按钮**（已移除；源码 `src/client/index.ts` 抬头只有「← 返回会话 + 标题」在左、右侧是分段控件 + 「＋ 新建任务」；任务列表顶部右侧只有搜索框 + 工作区下拉）。
- 常规更新靠 **10 秒轮询 + `rev` 比对**（`POLL_MS = 10_000`）；本地写操作（启停 / 保存 / 删除）后调 `refresh()` **局部刷新**，不等轮询。
- 相对时间、倒计时由客户端本地计时器渲染，不产生请求。

> ⚠️ **轮询 ≠ 每 10 秒重排**：排序键是 `nextSlotAt` / 状态 / 启停，一天只变几次；「10 分钟后 → 9 分钟后」这类相对时间是纯文本更新，**不触发重排、不触发动画**。否则每 10 秒全体抖动，动画就成噪音了。

### 4.5 动画规格（卡片「下去 / 上来」）

**自研 FLIP，不引包**：重排前记录每张卡片的 `getBoundingClientRect().top`（key = task id）→ 重排后测新 top → 用 `transform: translateY(delta)` 反向补偿 → 下一帧清除 transform 并挂 `transition: transform 260ms`，卡片即平滑滑到新位置。

| 场景 | 动画 |
|---|---|
| 排序变化（跑完的沉下去、下一个顶上来） | FLIP 位移，**只动画 top 真变了的卡片**（通常 1–3 张，不是全列表） |
| 状态灯变色 | `transition: background-color/color 200ms` |
| 运行中 | CSS `@keyframes` 转圈（零请求） |
| 展开 / 收起 | 测 `scrollHeight` 做高度过渡；被推挤的下方卡片复用同一套 FLIP 平滑下移 |
| 新增出现 / 删除消失 | 淡入 + 轻微上移 / 淡出 |

- 成本：只跑在位置变化的卡片上，几百条 × 10 秒一次可忽略。
- 降级：`prefers-reduced-motion` 开启时不播动画。

### 4.6 明确不做

- 不做 WebSocket / 长连接 / 每卡片订阅。
- 不做「轮询时逐任务查库」。
- **不把运行态写回任务定义 JSON**（破坏「设置是设置，运行是运行」，还会误触发快照与提示词版本的「内容变了才留」判定）。
- **不把任务定义迁入数据库**——与决策 25 冲突（登记表已删，定义真源 = 用户配置 JSON）。
- **不引入派生表 `task_runtime`**（用户 2026-09-30 拍板）：运行状态只放进程内存，启动时一次初始化，运行中增量维护；进程重启后由 `task_instances` 重建，无需额外持久化。

## 到点与延期显示（自历史决策并入）

- 已到点未派发 ⇒ 上界内显「运行中」、超上界显「延期」+ 悬浮原因；**延期只显徽标，不假装在跑**。
- 客户端不再有本地派生排序状态（钳位已删）。
