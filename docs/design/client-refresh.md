# 客户端刷新机制（轮询，非推送）

> **状态**：定型（2026-10-06）。推送方案待后续评审（用户原话「我们空了再来」）。
> **适用版本**：当前 `dsh-task-dispatch-table` 客户端（`src/client/*`）。
> **来源**：用户 2026-10-06 拍板「统一刷新机制」+ 本仓库 `dsh-capabilities.md`（宿主不推实例状态给客户端）。

## 一、事实前提（先读源码、勿猜）

宿主（DSH）**不会把「实例状态变化」推给客户端**：

- 服务端 `reconcile` 借 `ctx.on('session/event', …)` 得知某次执行跑到终态，再写 `task_instances`；这一步发生在**服务端**，客户端完全感知不到。
- 客户端只靠**轮询 HTTP** 拿最新数据。所以「任务跑完、开着的那一页状态没更新」这类问题，只能靠客户端自己轮询解决。

> 若将来要做「真·通知 / 推送」，需要**服务端改 SSE / WS**，是比轮询大得多的改动——本期不做，留待评审。

## 二、当前机制（单源、三处共用）

| 视图 | 刷新方式 | 触发 / 停止 |
|---|---|---|
| 任务配置（卡片三面板） | 每 **10s** 轮询 `GET /tasks/overview`，`rev` 比对，无变化不重渲 | 常驻 |
| 执行记录页 | 共享 hook `useInstancesRunningPoll` | 列表里**还有在跑的实例**（`isRunningStatus`）时每 **5s** 静默重载首屏；跑完即停 |
| 任务日程页 | 同上，共享同一 hook（重载当月） | 同上 |

- 轮询逻辑**只写一份**：`src/client/instances-poll.ts` 的 `useInstancesRunningPoll(hasRunning, reload)`。
  - `reload` 存进 ref：调用方每次渲染给新函数也不会反复重建 interval（否则频繁重渲的页面计时器会被不断重置、永远不触发）。
  - 只刷首屏、不切 `Loading`、不惊扰已展开的内容（`silent`）。
- 运行中视觉**只写一份**：`src/client/ui/running.ts`（`RUNNING_TONE` 蓝 + `RUN_PULSE_CLASS` + keyframe `dsh-tdt-run-pulse`）。任务配置 / 执行记录 / 日程三处都引用它，改一处即全局生效。

## 三、边界（别踩）

- 日历的「预计执行」条目按**当前任务配置现算**（`src/calendar-plan.ts`），不是 `task_instances` 行；刷新不影响它（它本来就不进 instances 表，决策 31 懒建行：到点才 INSERT，不预建、不回看）。
- 任务配置页的 10s 轮询是 `rev` 比对型（轻）；执行记录 / 日程的 5s 轮询只在「有在跑」时存在，跑完即停，不会无脑全量一直轮。
