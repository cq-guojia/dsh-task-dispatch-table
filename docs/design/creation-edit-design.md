# 新增任务 / 编辑任务：设计提纲（下一轮新会话专用）

> **这是什么**：任务表单 UI（决策 44–50）已封档后的**下一个议题**——「新增任务 / 编辑任务」这条功能线的数据面与设计。
> **怎么用**：新会话先读本文件 + [`data-model.md`](data-model.md) + [`decisions.md`](decisions.md) 相关条目，再按 §一 → §五顺序逐项拍板；拍定后把结论回写到对应的 design 文档与 PROGRESS。
> **本文件只列问题与现状，不写结论**——结论由新会话讨论产生。

---

## 〇、现状速览（讨论的前提事实）

| 面 | 现状 |
|---|---|
| 任务定义存放 | **settings 的 `tasksInline` 字符串**（整份 JSON 一把存；不是逐任务一行）。另有 state.db `meta` 表参与持久化主通道（决策：重装不丢） |
| 身份 | `id` = UUID，**保存时固化、运行时只认**（决策 30 闸门：无 id 补 UUID；UUID 必须命中现有表；非 UUID 整批拒） |
| 实例与日志 | state.db `task_instances` / `task_events` / `task_log` 三表（见 data-model.md §二） |
| 派发快照 | `InstanceSnapshot` 随实例行落库（决策 41）：改任务定义**不影响已落库实例** |
| 表单草稿 | `TaskEditorDraft`（client 侧，**仅新建态**）；`draftToDefinitionJson` 只做只读预览；**没有「定义 → 草稿」的反向映射**（编辑现有任务目前只能从空表单开始） |
| 附件 | 上传落盘插件数据根 `task-attachments/`（原始名 + 随机尾缀）；**与任务的持久化关联未做**，草稿层外不落库 |
| 提示词版本 | 有 UI（保存 / 回滚）与草稿内 `versions`，**未做持久化**（P3 未落地） |

## 一、数据库设计（先定这个，后面三项都依赖它）

1. **任务定义到底存哪**：继续整份 `tasksInline` 字符串？还是拆成独立表（`tasks` 表，一行一任务，字段列化 / 或 `definition_json` 列）？两处（settings + meta 表）是否要收敛成一处？
2. **表结构**（若拆表）：主键 = `id`（UUID）；`code` / `title` 是否冗余成列（便于列表排序与查重展示）；`enabled`、`schedule.*`、`target.*` 是否提列还是整份 JSON 存一列 + 关键字段冗余。
3. **唯一性与约束**：`code` 是否允许重复（现口径：只记录、不参与唯一）；`(id)` 之外要不要加 `(code)` 索引；删除是物理删还是 `deleted_at` 软删。
4. **执行记录与定义的关联**：执行行现在只存 `task_id`；要不要落 `def_revision` / `def_snapshot` / `run_type`（U5 已设计未拍板）——决定「点开一条执行记录能看当时的配置」能否实现。
5. **新表**：附件表（`task_attachments`：task_id / 路径 / 原名 / 大小 / 来源 / 落盘时间）、版本表（`prompt_versions`：task_id / 序号 / 内容 / 时间 / 备注）是否建、字段与索引。
6. **迁移与回滚**：存量 `tasksInline` 怎么一次性迁进新表；迁移失败 / 中途断电怎么办；是否保留旧字段做回退窗口。
7. **并发与一致性**：settings 写入（宿主作用域）与 SQLite 写入谁为准；两处不一致时的胜负规则；多人/多端同时改的冲突策略。
8. **备份与导出**：是否提供导出 JSON（备份 / 迁移 / 进 Git）；导入时的身份冲突（UUID 已存在）如何处理。

## 二、详细问题 (a) 文件保存：上传的文件怎么保存，放什么地方？

1. 落盘位置：继续插件数据根 `task-attachments/`？还是按任务分子目录（`task-attachments/<task_id>/`）？还是落进任务所属**工作区**（执行期 agent 直接可读）？三者取舍（跨任务复用 / 清理 / 权限 / agent 可见性）。
2. 与任务的关联：什么时候写入关联（保存任务时一起？还是上传即登记 + 任务保存时引用）？**孤儿文件**（上传成功但任务没保存）怎么清理（定时清扫 / 未引用标记 / 保留 N 天）。
3. 命名与去重：原始名 + 随机尾缀是否保留；同名重复上传是否覆盖；是否做内容哈希去重。
4. 规模约束：单文件上限（现 20MB）、单任务总量上限、扩展名白名单是否按任务可配。
5. 生命周期：删除任务时附件是否跟着删；停用任务保留附件；跨容器 / 挂载卷迁移时的路径基准（相对还是绝对）。
6. 执行期怎么用：消息里贴路径清单（默认方向）还是内容内联；链接型附件（工作区内已有文件）与上传型附件是否统一表现。

## 三、详细问题 (b) 版本管理：提示词的版本管理怎么做？

1. 存哪：文件系统（每任务一个目录，版本文件）还是数据库表？与决策「版本管理落文件系统（P3）」是否一致，还是改成入库（备份/事务更好）。
2. 版本粒度：只管**提示词**，还是整份任务定义（提示词 + 排期 + 附件 + 权限）都要版本？后者才能让「回滚到某次配置」成立。
3. 触发时机：手动「保存版本」？每次任务保存自动留版？两者都要（自动留 + 手动标注）？
4. 保留策略：条数上限（默认 20 版）+ 时间上限（30 天）+ 支持手动删（Q7 待拍板）；超限淘汰是否保护标注版。
5. 回滚语义：回滚是否立刻生效于任务定义；是否自动为「回滚前的当前值」再留一版（防误滚）；回滚是否影响在飞实例（按决策 41 应不影响）。
6. 展示：版本列表要看什么（时间 / 备注 / 差异）；要不要 diff 视图；谁能删。

## 四、详细问题 (c) 配置预览：预览的到底什么内容？

1. 预览对象：当前**草稿**生成的定义 JSON（未保存）？还是保存后落库的真值？两者差异（id 是否已分配、派生字段、cron 映射结果）。
2. 内容范围：是否含 `id`（新建时还没分配 ⇒ 预览里怎么表示）；是否含派生结果（cron 串、`schedule.start`、每 N 周锚点）；是否含表单里砍掉但 round-trip 保留的字段（`contract.validStatuses`）。
3. 与编辑的关系：预览是否可编辑（现为只读 + 复制）；若开放编辑，改完如何回填草稿、如何校验。
4. 语义澄清：它到底是「给高级用户看/核对任务定义」还是「给排查用看某次执行当时跑了哪份配置」（后者属 U5 的 `def_snapshot`）——两条需求要不要合并到一个入口。
5. 呈现：JSON 缩进 / 行号 / 复制；是否附人类可读摘要（排期说人话、模型、权限、重试）。

## 五、补充议题（agent 追加，供新会话一并拍板）

1. **编辑态数据面（最大缺口）**：`definitionToDraft` 反向映射尚未实现 ⇒ 编辑现有任务会从空表单开始，实测必踩。需定：结构化排期（档/粒度/时刻/每 N 周/星期/月日）如何从 cron + start 反解；反解不出来的（手改过的 cron）如何降级展示且**不丢原值**。
2. **保存链路**：新增 / 编辑 / 删除的 API 形态（`POST /tasks` 整批 vs 单条）；保存失败的回滚与提示位置；**部分成功**（附件已上传、定义被拒）的一致性。
3. **校验与必填**：任务名 / 提示词 / 工作区 / 排期的必填与错误提示；同批多条时的错误定位。
4. **改配置对在飞实例的影响**：明确「改完只影响后续刻度、在飞实例按快照走」（决策 41）在 UI 上怎么让用户看见；改了排期后已生成的未来刻度行要不要重算。
5. **立即执行 / 手动重试**：表单里要不要「立即跑一次」按钮（对应 U5 的 `run_type='manual'`）。
6. **导入导出与复制任务**：以现有任务为模板新建（复制定义、换 id）。
7. **权限档位的后续**（决策 50）：字段已落库，宿主开放 per-task 权限参数后改为下发；新会话确认是否保留消息约束作为兜底。
8. **审计**：谁在什么时候改了哪个任务（简易变更记录），与 `task_log` / `task_events` 的关系。
