# 状态机与依赖语义

本文覆盖任务实例的生命周期、依赖判定、以及必须补的健壮性机制。

## 1. 对账判定树

```
每个 tick 重新对账（取出 status = dispatched / running）
        │
        ├─ 会话还在跑 ──→ 继续等；租约超时则回收为 failed 并重试
        │
        └─ 会话已结束 ──→ 读「产物契约文件」
                            ├─ 存在 + status 合法 + mtime 新鲜 ──→ succeeded
                            └─ 缺失/不合法/过期 ────────────────→ failed（并通知人）
```

**所有对阵判定都是纯程序逻辑，零 token。**

## 2. 状态取值

| 状态 | 含义 | 下游怎么对待 |
|---|---|---|
| `pending` | 未到时间 / 前置未满足 | 等 |
| `dispatched` | 已派发，等会话确认建立 | 宽限期内等 |
| `running` | 会话在跑（带租约） | 等 |
| `succeeded` | 产物校验通过 | 依赖满足 |
| `failed` | 重试耗尽 / 产物校验失败 | 依赖不满足，**必须通知** |
| `skipped` | 当日窗口过期 / 上游失败 | **必须通知**（跳过 ≠ 正常） |
| `unknown` | 宽限期内无法确认（防双跑） | 下个 tick 再看 |

## 3. 依赖语义（两种）

| 语义 | 判定 | 缺了怎么办 | 适用 |
|---|---|---|---|
| `same_period` | 找**同一 logical date** 的上游实例 | 跳过 | 日榜 → 日报 |
| `latest_success` | 找**最近一次成功** + 新鲜度上限（如 ≤ 8 天） | 超上限才跳过 | 月榜 → 报告 |

⚠️ **归属用「计划时刻 `scheduled_at`」，不是「实际开始时间」**——任务 9:00 计划、因等前置 11:00 才跑，它仍属**今天**。这与「过窗口切次日」的规则天然咬合。

## 4. 一个必须避开的坑

> **「查会话是否存在」不能判断它是否在跑。**

DSH 会话是**持久化**的（日志落盘），`session/disposed` 只是把它从**内存 store** 移除。
所以「跑完了」和「从没建起来」**磁盘上都在**——用存在性判断会把跑完的误判成派发失败，**重复派发**。

**修法**：拆成两个独立信号

- 收到过 **`session/created`** → 派发成功
- 收到过 **`session/disposed`** / `turn/end` → 已结束
- 插件在进程内，`ctx.on('session/event')` 能收到**所有会话的所有事件** ⇒ **不用轮询**，轮询只作重启后兜底

## 5. 五个必须补的机制

| # | 机制 | 不做会怎样 |
|---|---|---|
| 1 | **产物三查**：存在 + `status` 字段合法 + **mtime 晚于本次派发** | 第 ③ 条不做 → 读到**上次的旧产物**，把失败**误判成成功** |
| 2 | **租约**（running 超时回收） | 会话卡死（等审批/长工具调用）→ 永久停在 running |
| 3 | **`unknown` 态** | 宽限期内不确认也不判失败，否则双跑 |
| 4 | **重发幂等** | agent 可能已干了一半，重复派发会做两遍 |
| 5 | **启动扫描对账**（= K8s resync） | host 重启期间 `disposed` 事件全丢 ⇒ 状态永远卡住 |

## 6. 已弃用的方案

| 弃用 | 原因 |
|---|---|
| 让调度器**发消息问会话**「完成了吗？回 Y/N」 | ① 又唤起一次 agent，白烧 token ② **agent 会撒谎** ③ 会话若已 disposed 未必收得到 |
| **事件驱动**（前置完成时主动唤醒下游） | 「拉」比「推」可复用——加下游不改上游，见 [decisions.md](decisions.md) 决策 8 |
