## 二、结论（决策 33）：依赖判定简化

核心议题：上游「错过 / 失败 / 在跑」会不会导致下游复用旧产出。
**最终拍板（用户 09-26）：不引入水位线，只加一条简单判定 + 告警。**

### 2.1 `latest_success` 判定改为「上游最近一条必须 `succeeded`」

取上游**最近一条实例**（按 `scheduled_at` DESC，**不分状态**）：

| 上游最近一条 | 下游怎么办 |
|---|---|
| `succeeded` | 放行 ✅ |
| `dispatched` / `running` / `unknown` | 阻塞，等（记 `dep_blocked`） |
| `failed` | 阻塞 —— 失败向下游传播（决策 10） |
| 一条都没有 | 阻塞 |

对照（本议题的核心）：

| 上游本轮 | 旧行为 | 新行为 |
|---|---|---|
| 成功 | 放行 | 放行 ✅ |
| **失败** | 跳过失败行、拿更早的成功 ⇒ **用旧数据跑** ❌ | **阻塞** ✅ |
| **在跑** | 拿更早的成功 ⇒ 用旧数据跑 ❌ | **阻塞等** ✅ |
| 错过/跳过（无记录） | 拿上次成功 ⇒ 用旧数据跑 | 放行（拿上次成功）⚠️ 已知风险，见 2.3 |

### 2.2 「上游错过」只告警、不拦

放行时若发现「上游这份成功的时刻 **不晚于** 下游上次执行的时刻」⇒ 说明下游上次跑时
这份数据就已经在了 ⇒ 记 `task_log` **warn**：`上游无新产出，本次复用 <时刻> 的旧产出`。
- 判据只比「下游上次执行时刻」与「上游成功时刻」，**不新增字段**。
- 下游首次运行无可比对象 ⇒ 不告警。

### 2.3 已知风险（用户明确接受）

「上游错过 / 跳过」时下游仍会用上一次的成功产出执行。理由：正常运行的服务器上概率很低；
且上游自身的 `missed_slot` / `failed` 有留痕可查。**不为此拦住下游。**

### 2.4 不做的事（明确砍掉，避免后人重复设计）

- ❌ **水位线（消费水位）方案** —— 曾一度拍板，后发现与「周报 → 日报」类快照复用诉求
  冲突（会把每天跑的下游挡成每周跑一次），已废弃。过程见第四节。
- ❌ `task_instances.consumed_upstream` 列
- ❌ `depends_on.consumeOnce` 开关
- ❌ `freshness` 字段（已从 `tasks.ts` schema 删除，见决策 33）

### 2.5 必须修的 bug

`getLatestSuccess` 现为 `ORDER BY logical_date DESC`——只到「日」不含时分秒，
同一天多次成功取哪条不确定。本方案强依赖「最近一条」取对 ⇒ **必须改按 `scheduled_at` 排序**。

## 四、讨论过程：为什么放弃了水位线

1. **起因**：担心上游「错过」后 `latest_success` 复用旧产出。
2. **一度拍板水位线（方案 A）**：下游记录每个上游「上次消费到哪个节点」，只有出现
   「未被消费的新成功」才放行。
3. **用户提出「周报 → 日报」场景，暴露硬伤**：A 每周一跑、B 每天跑并复用周一的数据。
   水位线下，周二~周日 A 无新成功 ⇒ B 被判「没有新货」⇒ **B 一周只跑一次**，与诉求相反。
4. **结论**：两种诉求相反——「等新货才跑」（月报 → 季报）需要水位线；
   「每次用上游最新那份」（周报 → 日报）会被水位线误挡。与其加开关让用户选，不如**统一简化**。
5. **最终**：只判「上游最近一条是否 `succeeded`」，堵住「失败」与「在跑」两个大头；
   「错过」的情况接受复用并告警。
