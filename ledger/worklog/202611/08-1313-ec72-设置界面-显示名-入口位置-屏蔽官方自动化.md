## Process

### 一、官方「自动化」是谁（宿主 0.2.2-rc.1，源码核实）

- 官方自动化任务界面 = `@deepseek-ai/dsh-client-ui-schedule`；组合行 `id: ui-schedule`、`name: '@deepseek-ai/dsh-client-ui-schedule'`，声明在 `@deepseek-ai/dsh-web-app@0.2.2-rc.1` `cordis.patch.yml:403-404`。
- 它把侧栏入口注册进 `sidebar.panellist`（`id: schedules`、`order: 10`，见该包 `lib/client.js`）。**不在** `PROTECTED_PLUGINS` 名单（`dsh-official-bundles@0.2.2-rc.1` `lib/index.js:64-82`），可停用。
- 官方 slots **没有**「隐藏他人条目」的 API：侧栏行来自 `ctx.slots.entriesOfSlot("sidebar.panellist")`，只有注册方自己 dispose 才会消失（`dsh-client-ui-renderer@0.2.2-rc.1` `lib/client.js`，列表分支只有 `opts.only` 过滤）。⇒ 只能停用整条官方 UI 包，或 CSS 藏行（弃用）。

### 二、两条候选路线与拍板

- **A1（拍板采用）**：屏蔽/放开都走官方 `pluginManager.setPluginEnabled`。默认不屏蔽天然成立（不写就是启用）。卸载回滚要在我们插件的 dispose 里再调一次。
- **A2（弃用）**：把我们自己的 `cordis.patch.yml` 里写死 `- id: ui-schedule, disabled: true`，profile 只写「放开」。源码上成立（层序 / 拆层即恢复都核过），但等于我们的包替用户藏掉官方功能，且「默认不屏蔽」要靠首次运行写一次 `disabled:false` 才成立——用户 2026-11-08 认可「A1 更正规」，选 A1。

### 三、A1 依赖的源码事实

- 写入口：`setPluginEnabled(entryId, enabled)`（`dsh-plugin-manager@0.2.2-rc.1` `lib/index.js:2669-2676`）→ `writePluginEnabled` 往 profile `cordis.patch.yml` 追加/改 `{id, disabled}`（同文件 `:1139-1186`），冗余覆盖项会被 `implied()` 自动删掉。
- 层序：bundle 层 → profile → home → CLI（`dsh-app-boot@0.2.2-rc.1` `lib/index.js:1908-1917`），后层覆盖前层。
- **被禁用条目仍可寻址**：loader 仍为每行建 Entry（disabled 只是没有 fiber），`ctx.loader.entries()` 照样枚举，插件清单 `enabled: !entry.disabled`（`dsh-host-plugin-inventory@0.2.2-rc.1` `lib/index.js:124,139`）⇒ 停用后还能用同一接口放开。
- 可寻址三前提：目标行是根 include 的**直属**行（`actual?.parent.tree.ctx.fiber.entry?.id === 'include'`）、组合行带 `name` 且与模块名逐字一致、`entryId` 用带前缀的 `include:<row id>`（`dsh-plugin-manager` `lib/index.js:2108-2111`）。
- 无 HMR 时 `setPluginEnabled` 只 compose 不重载，返回 `restart-required`/`no-hmr`，重启才真生效（同文件 `:3129-3134`）。

### 四、已知风险

- 卸载回滚要在 dispose 里再调 `setPluginEnabled`，而每次写操作都包在 `withFileLock(profile/package.json, waitMs=120s)`（`dsh-plugin-manager` `lib/index.js:3187`）——卸载正是外层那次操作持锁 reload 时触发的，同步 await 会等锁，只能延后 fire-and-forget；宿主进程紧接退出时这一枪可能没打出去。兜底：被禁用的行在插件页仍可见可点，用户手动开回来。
- 官方若改了 `ui-schedule` 行 id，我们的覆盖行会**静默 warn 失效**（`dsh-app-boot` `lib/index.js:541-543`），升级宿主需复核。

## Conclusion

已实现（构建 / 冒烟 763 项 / 双端 typecheck 全绿）：

- 配置三个字段（`src/config.ts`）：`displayName`、`entryMode`（默认 `first` = 侧栏一级菜单）、`hideOfficialSchedule`（默认 `false` = 不屏蔽）；沿用本插件自有 HTTP 通道与状态库，没用宿主 volatile 配置面。
- 设置区版式按 `dsh-task-ledger` 的 `config-panel.ts` 逐条对齐：两列网格（三个字段各占半格，第三个落第二行左半）、核心 `Input`/`Picker`/`Chip`/`Button`、改过才出「自定义」+「恢复默认」、保存与两个链接同排。「屏蔽官方自动化」用两档下拉（不屏蔽 / 屏蔽）。
- `/config` 白名单扩到 boolean，`entryMode` 加枚举校验（`src/index.ts`）。
- 设置区表单（`src/client/config-panel.tsx`）：显示名 + 入口位置一行两列、屏蔽官方自动化开关、保存 + GitHub + 组件库一排；保存成功后立刻重挂侧栏入口。
- 侧栏入口位置与显示名（`src/client/sidebar-entry.ts`）：`more` ⇒ `sidebar.panellist.actions`，`first` ⇒ `sidebar.panellist`；标题空则回落 `panelTitle`。
- 官方自动化开关（`src/official-schedule.ts`）：`pluginManager.setPluginEnabled` 双向 + 启动对账 + 卸载延后回滚。
- 冒烟：旧的「详情页无表单」反断言换成「三字段 + 保存 + 两个链接」，另加一条「开关走 pluginManager、默认更多 + 不屏蔽」守卫。
- 宿主结论回写 `docs/design/external/official-schedule-toggle.md`，并登记进 `docs/README.md`。

留的坑：卸载回滚靠 dispose 里的延后调用，宿主进程紧接退出时不保证跑到（兜底：插件页手动开回那一行）；`ui-schedule` 行若被官方改名，屏蔽开关会静默失效（只有一条 warn 日志）。
